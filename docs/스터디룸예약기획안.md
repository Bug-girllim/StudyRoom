# StudyRoom — 스터디룸 예약 관리 시스템 최종 기획안

> **형태:** Java 21 · Maven · JDBC · MySQL 8.0.16 이상 · 콘솔 프로그램  
> **기간/인원:** 1일 / 4명  
> **목표:** 회원가입 → 로그인 → 룸·시간대 조회 → 중복 없는 자동 예약 → 본인 예약 변경·취소

## 1. 프로젝트 개요

회원이 로그인 후 스터디룸, 이용 날짜, 사전에 등록된 고정 타임슬롯을 선택해 예약하는 시스템이다. **같은 룸·날짜·슬롯에는 한 건만 예약**할 수 있으며, 조건을 만족하면 관리자 승인 없이 즉시 확정된다. 예약 1건은 해당 룸 전체 이용을 뜻하며, 수용 인원은 표시 정보일 뿐 좌석별 예약에는 활용하지 않는다.

### 사용자별 권한

| 구분 | 기능 |
|---|---|
| 비로그인 | 회원가입, 로그인 |
| 회원 (`USER`) | 룸·슬롯 조회, 본인 예약 등록·조회·변경·취소, 본인 이름·연락처 수정, 로그아웃 |
| 관리자 (`ADMIN`) | 회원 목록·수정·삭제, 룸·슬롯 등록·조회·수정·삭제, 전체 예약 조회, 로그아웃 |

- 회원가입 계정은 항상 `USER`이며 관리자는 초기 샘플 데이터로 준비한다.
- 관리자는 예약 승인·강제 취소를 하지 않는다.
- `Controller`는 Java 요청 처리 계층으로, 관리자 역할인 `ADMIN`과 다르다.

## 2. 핵심 정책

| 항목 | 확정 규칙 |
|---|---|
| 접근 | 로그인 전 룸·슬롯·예약 조회 불가 |
| 중복 예약 | `(room_id, reservation_date, slot_id)`가 동일하면 거절. DB 복합 `UNIQUE`도 적용 |
| 다른 예약 | 룸 또는 날짜가 다르면 같은 슬롯 예약 가능. 동일 회원의 다른 룸 동시간 예약은 제한하지 않음 |
| 날짜 | 오늘 또는 미래만 허용. 당일 이미 시작된 슬롯인지는 검사하지 않음. 최대 예약 기간 제한 없음 |
| 예약 승인 | 검증 통과 후 INSERT 즉시 확정. 승인/예약 상태 컬럼 없음 |
| 예약 변경 | 본인 예약만 변경. 기존 예약 ID를 중복 검사 대상에서 제외하고, 중복 시 원래 값 유지 |
| 예약 취소 | 본인 예약 행을 DELETE. 취소 이력 없이 같은 조합 재예약 가능 |
| 참조 데이터 삭제 | 예약과 연결된 회원·룸·슬롯 삭제 불가 (`ON DELETE RESTRICT`) |
| 타임슬롯 | 모든 룸이 공통 슬롯 사용. 시작 시각은 종료보다 빨라야 하며 다른 슬롯과 시간 겹침 금지 |
| 슬롯 수정·삭제 | 예약이 한 건이라도 참조하면 수정·삭제 불가(예약 날짜가 과거여도 동일) |
| 목록 | 목록 조회만 구현. 상세·검색·정렬 옵션 제외(슬롯 목록은 시작 시간순) |
| 입력 오류 | 안내 메시지 출력 후 현재 메뉴로 복귀, 프로그램 종료 금지 |
| 비밀번호 | 실습용 가상 계정만 사용. 해시 없이 문자열 비교(BCrypt 미사용). 실제 서비스에는 사용 금지 |

**시간 겹침 판정:** `새 시작 < 기존 종료 AND 새 종료 > 기존 시작`. 수정 시 자기 `slot_id` 제외. `09:00~11:00`과 `10:00~12:00`은 충돌하지만 `11:00~13:00`은 허용한다.

## 3. 기능 명세 및 담당

담당 A~D는 역할 구분이며 실제 이름 배정은 별도로 정한다.

| ID | 담당 | 기능 | 입력·처리·출력 및 주요 예외 |
|---|---|---|---|
| F-01 | A | 회원가입 | 아이디·비밀번호·이름·연락처 입력 → 필수값·숫자 연락처·아이디 중복 검사 → `USER` 등록. 중복·형식 오류 안내 |
| F-02 | A | 로그인/로그아웃 | 아이디·비밀번호 일치 시 세션에 회원 ID·역할 저장 후 권한별 메뉴 이동. 로그아웃 시 세션 초기화. 로그인 오류 시 통합 안내 |
| F-03 | A | 회원 목록 | ADMIN만 전체 회원 조회. 비밀번호 미출력, 빈 목록 안내 |
| F-04 | A | 회원 수정 | USER는 자기 이름·연락처, ADMIN은 지정 회원의 이름·연락처 수정. 아이디·암호·역할 수정 불가 |
| F-05 | A | 회원 삭제 | ADMIN이 회원 ID로 삭제. 없는 회원·연결 예약·로그인한 관리자 본인 계정이면 거절 |
| F-06 | B | 룸 등록 | 이름·위치·수용 인원 입력 → 필수값·이름 중복·수용 인원(1 이상 정수) 검증 → 등록 |
| F-07 | B | 룸 목록 | 번호·이름·위치·수용 인원 표시, 빈 목록 안내 |
| F-08 | B | 룸 수정 | 룸 번호와 모든 새 값 입력 → 존재·이름 중복(본인 제외)·수용 인원 검사 → 수정 |
| F-09 | B | 룸 삭제 | 번호로 삭제. 연결 예약이 있으면 거절 |
| F-10 | C | 예약 등록 ★ | 룸 번호·날짜(`yyyy-MM-dd`)·슬롯 번호 입력. 로그인 회원 ID 자동 사용 → 유효성·중복 확인 → INSERT 즉시 확정. 실패 시 저장하지 않음 |
| F-11 | C | 예약 목록 | USER는 본인 것만, ADMIN은 전체 조회. 예약 번호·룸·날짜·시간대 표시, 관리자 목록에는 회원 번호도 표시 |
| F-12 | C | 예약 변경 ★ | 본인 예약 번호와 **새 룸·날짜·슬롯 전체** 입력 → 소유권·유효성 확인 → 자기 예약을 제외한 중복 검사 → UPDATE |
| F-13 | C | 예약 취소 | 본인 예약 번호 확인 → 소유권 검증 → DELETE. 다른 회원 예약은 거절 |
| F-14 | D | 슬롯 등록 | 시작·종료(`HH:mm`) 입력 → 형식·시각 순서·다른 슬롯과 겹침 검사 → 등록 |
| F-15 | D | 슬롯 목록 | 슬롯 번호·시작·종료 시간 조회(시작 시간순) |
| F-16 | D | 슬롯 수정 | 슬롯 번호·새 시작·종료 입력 → 예약 참조 확인 → 본인 슬롯 제외 겹침 검사 → 수정 |
| F-17 | D | 슬롯 삭제 | 슬롯 번호 입력 → 예약 참조 없을 때 삭제 |

**공통 실패 안내 원칙:** 존재하지 않는 번호, 권한/소유권 위반, 잘못된 숫자·날짜·시간 형식, 과거 날짜, 중복 예약, 시간 겹침, 참조된 데이터 삭제·수정은 각각 이유를 안내한다. 대표 문구는 `이미 예약된 시간입니다.`, `다른 시간대와 겹칩니다.`, `본인 예약만 변경할 수 있습니다.`, `연결된 예약이 있어 삭제할 수 없습니다.`로 통일한다.

## 4. 콘솔 메뉴

```text
[시작] 1. 회원가입  2. 로그인  0. 종료

[회원]
1. 스터디룸 목록       2. 타임슬롯 목록
3. 예약 신청           4. 내 예약 목록
5. 내 예약 변경        6. 내 예약 취소
7. 내 정보 수정        0. 로그아웃

[관리자]
1. 회원 관리           2. 스터디룸 관리
3. 타임슬롯 관리       4. 전체 예약 목록
0. 로그아웃
```

관리자 관리 메뉴의 하위 화면은 목록·수정·삭제, 필요할 경우 등록 메뉴를 둔다. **회원 관리에는 회원 등록 메뉴가 없고**, 룸·슬롯 관리에는 등록 메뉴가 있다.

## 5. 데이터베이스 설계

### `member`

| 컬럼 | 타입 | 제약·비고 |
|---|---|---|
| `member_id` | BIGINT | PK, AUTO_INCREMENT |
| `login_id` | VARCHAR(50) | NOT NULL, UNIQUE |
| `login_password` | VARCHAR(100) | NOT NULL, 실습용 평문 |
| `member_name` | VARCHAR(50) | NOT NULL |
| `phone` | VARCHAR(20) | NOT NULL |
| `member_role` | VARCHAR(10) | NOT NULL, CHECK (`USER`/`ADMIN`) |

### `study_room`

| 컬럼 | 타입 | 제약·비고 |
|---|---|---|
| `room_id` | BIGINT | PK, AUTO_INCREMENT |
| `room_name` | VARCHAR(100) | NOT NULL, UNIQUE |
| `location` | VARCHAR(100) | NOT NULL |
| `capacity` | INT | NOT NULL, CHECK (`capacity >= 1`), 표시용 |

### `time_slot`

| 컬럼 | 타입 | 제약·비고 |
|---|---|---|
| `slot_id` | BIGINT | PK, AUTO_INCREMENT |
| `start_time` | TIME | NOT NULL |
| `end_time` | TIME | NOT NULL, CHECK (`start_time < end_time`) |

### `reservation`

| 컬럼 | 타입 | 제약·비고 |
|---|---|---|
| `reservation_id` | BIGINT | PK, AUTO_INCREMENT |
| `member_id` | BIGINT | NOT NULL, FK → `member` |
| `room_id` | BIGINT | NOT NULL, FK → `study_room` |
| `slot_id` | BIGINT | NOT NULL, FK → `time_slot` |
| `reservation_date` | DATE | NOT NULL |

- 관계는 회원·룸·슬롯 각각 **1:N 예약**이다.
- `reservation(room_id, reservation_date, slot_id)`에 복합 `UNIQUE`를 설정한다.
- 예약의 3개 FK에는 `ON DELETE RESTRICT`를 적용한다. `status`, `cancelled_at`은 만들지 않는다.
- `CHECK`가 적용되는 MySQL **8.0.16 이상**을 사용하고 Service에서도 같은 유효성 검사를 수행한다. 슬롯 사이의 겹침은 Service/DAO 쿼리로 검사한다.
- Java 자료형은 ID=`long`, 날짜=`LocalDate`, 시각=`LocalTime`, 수용 인원=`int`를 사용한다.

### 초기 데이터 (`sql/sample-data.sql`)

각 테이블 **5행 이상**: 회원 5명 이상(ADMIN 1명, USER 4명 이상), 룸 5개 이상, 슬롯 5개 이상, 예약 5건 이상. 기본 슬롯은 다음과 같다.

| 슬롯 | 이용 시간 |
|---|---|
| 1 | 09:00~11:00 |
| 2 | 11:00~13:00 |
| 3 | 13:00~15:00 |
| 4 | 15:00~17:00 |
| 5 | 17:00~19:00 |

샘플 INSERT는 `member`·`study_room`·`time_slot`을 먼저, `reservation`을 나중에 수행한다. 예약은 충돌 없는 미래 날짜로 준비하고, SQL 재실행 방법을 README에 기재한다. 실제 개인정보·비밀번호를 샘플에 사용하지 않는다.

## 6. 코드 구조 및 팀 협업

### 5계층 구성

| 담당 | DTO | DAO | Service | Controller | View |
|---|---|---|---|---|---|
| A 회원 | `MemberDTO` | `MemberDAO` | `MemberService` | `MemberController` | `MemberView` |
| B 룸 | `RoomDTO` | `RoomDAO` | `RoomService` | `RoomController` | `RoomView` |
| C 예약 | `ReservationDTO` | `ReservationDAO` | `ReservationService` | `ReservationController` | `ReservationView` |
| D 슬롯 | `TimeSlotDTO` | `TimeSlotDAO` | `TimeSlotService` | `TimeSlotController` | `TimeSlotView` |

- **DTO** 데이터 전달 / **DAO** JDBC·SQL / **Service** 비즈니스 검증 / **Controller** 요청·결과 연결 / **View** 콘솔 입출력.
- 공통 클래스는 `Application`·`LoginSession`(A), `JDBCTemplate`(B)로 구분한다. **`DBUtil`을 이미 구현한 경우**에는 JDBC 연결용 `JDBCTemplate`과 역할을 혼동하지 않고 실제 클래스명·역할을 팀에서 통일한다. 별도 `QueryUtil`은 필수 아님.
- 기본 패키지: `com.studyroom`. SQL은 `sql/schema.sql`, `sql/sample-data.sql`에 둔다.
- DB 비밀번호가 있는 `../src/main/resources/db.properties` 등은 `.gitignore`로 보호한다.

### DAO 메서드 계약

| DAO | 메서드 |
|---|---|
| `MemberDAO` | `findByLoginId(String)`, `findById(long)`, `findAll()`, `insert(MemberDTO)`, `update(MemberDTO)`, `delete(long)` |
| `RoomDAO` | `findById(long)`, `findAll()`, `existsByName(String, long excludeId)`, `insert(RoomDTO)`, `update(RoomDTO)`, `delete(long)` |
| `TimeSlotDAO` | `findById(long)`, `findAll()`, `existsOverlap(LocalTime, LocalTime, long excludeId)`, `insert(TimeSlotDTO)`, `update(TimeSlotDTO)`, `delete(long)` |
| `ReservationDAO` | `findById(long)`, `findByMemberId(long)`, `findAll()`, `existsDuplicate(long roomId, LocalDate date, long slotId, long excludeId)`, `insert(ReservationDTO)`, `update(ReservationDTO)`, `delete(long)` |

단건 조회는 DTO 또는 `null`, 목록 조회는 `List<DTO>`(없으면 빈 리스트), 중복 확인은 `boolean`, 쓰기는 `boolean`을 반환한다. DB 예외는 단순 `false`로 숨기지 않는다. `excludeId=0`은 신규 등록이며, 수정 시 자신의 ID를 전달한다. **서로 다른 영역에서 호출할 Service 메서드명·오류 반환 방식은 통합 전에 합의**한다.

### 역할과 Git

| 담당 | 개발 영역 | 공통 책임 |
|---|---|---|
| A | 회원·로그인 | `Application`, `LoginSession` |
| B | 스터디룸 | DB 연결 클래스, ERD·`schema.sql`·`sample-data.sql` |
| C | 예약 | 예약 중복 검증 |
| D | 타임슬롯 | 슬롯 시간 겹침 검증, 통합 테스트 진행 |

공통 뼈대를 `main`에 올리고 `feature/member`, `feature/room`, `feature/reservation`, `feature/timeslot`에서 개발해 PR로 병합한다. `develop` 브랜치는 사용하지 않는다. 공통 파일은 지정 담당자 중심으로 수정한다.

## 7. 테스트 기준

| 영역 | 필수 테스트 |
|---|---|
| 회원·권한 | 가입/로그인 성공, 중복 아이디·오류 비밀번호 거절, 본인 정보 수정, 관리자의 회원 관리, 관리자 자기 계정 삭제 거절 |
| 룸 | 등록·목록·수정·삭제, 이름 중복 거절, 수용 인원 0 이하/문자 거절, 예약 연결 시 삭제 거절 |
| 예약 | 정상 예약, 같은 룸·날짜·슬롯 중복 거절, 다른 룸/날짜 허용, 과거·형식 오류·없는 ID 거절 |
| 예약 변경·취소 | 자기 예약 동일 값 수정 허용, 중복 조합으로 변경 거절 및 기존 값 유지, 타인 예약 변경·취소 거절, 취소 후 재예약 허용 |
| 슬롯 | 등록·목록·수정·삭제, 시작 ≥ 종료 거절, 시간 겹침 거절, 경계 일치 허용, 수정 시 자기 슬롯 제외, 예약 참조 시 수정·삭제 거절 |
| 통합·DB | 메뉴 문자·없는 번호 입력에도 계속 실행, 테이블당 최소 5행, PK/FK/UNIQUE/CHECK 점검, USER/ADMIN 메뉴 분리 |

## 8. 개발 일정 및 완료 기준

| 시간 | 작업 |
|---|---|
| 0~1시간 | 기획·역할·DAO 계약·패키지 합의 |
| 1~2시간 | ERD·스키마·샘플 5행씩·DB 연결 확인 |
